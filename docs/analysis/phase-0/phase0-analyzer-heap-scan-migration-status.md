- **`EventLeakAnalyzer`** ([EventLeakAnalyzer.cs](../../../src/DumpDetective.Analysis/Analyzers/EventLeakAnalyzer.cs)) — migrated to `IHeapIndexScanParticipant` via explicit interface implementation (the class is `public` but `HeapEntry` is `internal`, so `BeforeHeapIndexScan`/`OnHeapEntry`/`OnHeapIndexScanCompleted` are implemented explicitly rather than as public members). Rather than adding a bulk/chunked participant mode to the dispatcher (the option this doc originally flagged as a prerequisite), `EventLeakFastScanner` gained a single-entry `ScanEntry(in HeapEntry entry, ...)` method that factors the per-object body out of its existing `SinglePassScan`/`Scan` loop — `Scan` now just calls `ScanEntry` per entry, and the dispatcher's serial per-entry callback calls the exact same method. This sidesteps the parallelism concern entirely: the migrated path only replaces *how* entries are fed to the scanner (dispatcher push vs. internal pull), not the per-object scan logic itself, so the scanner's own `Parallel.For`-based chunking (used elsewhere in the file) is untouched. `BeforeHeapIndexScan` builds the root-hint map, static-field/delegate tracking sets, and a fresh `EventLeakFastScanner`; `OnHeapEntry` forwards to `ScanEntry`, accumulating into per-instance fields (`_participantGroupAcc`, `_participantEventsScanned`, `_participantPublisherInstances`, etc.). `FindEventLeaks` branches on `cache.TryGetHeapIndex(out _) && _participantScanSucceeded`: true reads back the participant-accumulated state directly; false (no on-disk index, or the dispatcher's isolated per-participant failure path) falls back to building a fresh `EventLeakFastScanner` and calling `Scan(...)` directly, same as before migration. `SweepModuleStaticFields` (module-level static-only publisher sweep) is untouched and runs after either path. Existing discrepancy/unit tests for `EventLeakAnalyzer` continue to pass unmodified.

## Straightforward — single self-contained disk-index loop, non-scan branches untouched

Directly mirrors `DbConnectionAnalyzer`'s shape: one `EnumerateIndexedEntries()`/
`EnumerateIndexedEntriesAsTuples()` loop, any other data-source branch (live-heap fallback,
prebuilt-dedup path) stays untouched by the migration.

_(no analyzers remaining in this bucket — `StringAnalyzer` moved to Completed above)_

## Moderate — multiple scan sites, needs its own design pass

Still a single participant-shaped migration, but each analyzer has more than one logically
distinct scan site over the same index; folding them into one `OnHeapEntry` callback needs care
to avoid silently changing which entries each sub-metric sees.

_(no analyzers remaining in this bucket — `CollectionAnalyzer` moved to Completed above; it
turned out to have only one real scan site)_

## Moderate-hard — sequential path migratable, parallel path stays separate

Both have a `RunSequentialXxxScan` (disk-index, single loop — migratable) and a separate
`RunParallelXxxScan` using `Parallel.ForEach` over `heap.Segments` for the no-index case (stays
untouched/parallel). The sequential methods are large (60–150+ lines) with several supporting
dictionaries/counters that would all need to become instance fields — doable, but each needs a
careful, isolated pass with full before/after re-reads.

_(no analyzers remaining in this bucket — `HangAnalyzer` moved to Completed above)_
