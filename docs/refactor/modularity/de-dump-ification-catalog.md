# De-dump-ification catalog

Phase 0 item 2 (see [phase-0-foundation.md](phase-0-foundation.md)): catalog everything that
assumes a single ClrMD dump is the only input, with a disposition for each — *generalize*
(becomes artifact-neutral), *becomes-a-dump-source-detail* (moves behind `IArtifactSource`,
[source-model.md § 2](source-model.md#2-artifact--the-unit-of-input)), or *deleted* (subsumed by
the session model, [source-model.md § 1](source-model.md#1-the-reframe)). Hand-compiled, not
scripted — unlike [contract-surface-inventory.md](contract-surface-inventory.md), assigning a
disposition is a judgment call, not a mechanical extraction. Each entry cites where it was verified
so it can be re-checked as the codebase moves.

## What this confirms, in aggregate

- Every "deleted" entry above (#2, #3, #4, #8, #12) is already independently named in
  [modularity-plan.md § 5](../modularity-plan.md#5-what-this-deletes) or § 8 — this audit found no
  *new* deletion candidates at the orchestration/pipeline layer, only confirmed the existing list
  against current source and added the missing `IAnalysisStage`/`StagedPipelineRunner`/
  `PerDumpExecutionService` detail the plan names at a coarser grain.
- The two genuinely new findings are **#5** (the storage/container layer is *already*
  source-neutral and shared with trace — only path-naming policy remains dump-specific, a smaller
  gap than the plan assumed) and **#7** (zero analyzers touch `RuntimeFacade` directly — a risk
  that didn't materialize, because item 1's SDK retyping already intercepts that path). Both
  reduce, not add to, the estimated de-dump-ification effort.
- **#6/#10** (CLI request/options shape) is the one area this audit surfaced that isn't already
  named anywhere in the modularity plan at the field level — worth folding into whichever phase
  ends up owning `InvestigationDefinition`/session construction from CLI args (Phase 1 SDK schema
  or Phase 4 orchestration, not decided here).
